## 总体评价

代码整体质量**高于个人项目平均水准**:任务持久化与重启恢复、半成品原子改名、取消语义(含对"引擎管道写满死锁"的分析注释)、ffmpeg 常驻管道 `-nostdin` 的坑、uvicorn 事件循环的版本兼容,都处理得有理有据;注释普遍解释"为什么"而不是"是什么"。核心链路(嵌入→自检→提取→码本)的端到端一致性(SHA-256 派生、bit 序、码本 v1/v2 兼容)经得起推敲。

## P1 —— 建议尽快修复

### 1. 提取 worker 的 `request()` 无互斥:预热与提取并发读同一 stdout,任务可能永久挂起

**位置**:`webui/app.py:257-274`(`EngineWorker.request`)、`app.py:276-284`(`warm_async`)、`app.py:491`(启动即预热)、`app.py:376`(嵌入前 `WORKER.kill()`)。

**状态:已于 2026-09-06 修复并回归验证**(见下)。

**问题**:`warm_async` 在后台线程调用 `WORKER.request()`,而提取任务在队列线程调用 `WORKER.request()`。两者会对**同一个** `proc.stdout` 并发 `readline()`。管道每行只会被其中一个线程读到:

- 若预热线程抢到提取任务的 result 行,它会因 id 不匹配而丢弃并继续阻塞读;提取线程永远等不到自己的 result → **任务卡在"运行中"直到重启后端**。
- 更糟的变体:两个线程同时进入 `ensure()`,在 worker 尚未存活时**各自 spawn 一个 engine_worker 进程**——`self.proc` 被覆盖,第一个进程泄漏(常驻显存,两个进程各占 45% 显存上限,逼近 OOM)。

**触发窗口很大**:每次嵌入任务开始前 worker 被杀、结束后 `warm_async()` 立即重新拉起并预热(模型加载约 10~30s)。而"嵌入完成后立刻去提取刚出的成品"正是最常见的工作流,提取请求落在这个窗口内就会竞态。后端启动时的预热窗口同理。

**修复方案(已实施)**:① `EngineWorker.request()` 加请求级互斥锁(`rlock`,覆盖 ensure + send + 读完 result 全程),预热与业务请求自然串行,`ensure()` 的双进程竞态一并消除;② 原 `_readline_timeout` 每次超时都会泄漏一个阻塞在读 stdout 的守护线程,该线程会抢走下一个请求的首行响应(同理导致挂起,且加锁后它会永久占住锁),已整块替换为"单读取线程 + 行队列(`_start_reader` + `_outq`)":每个 worker 进程一个专用读线程,EOF 投 `b""` 哨兵,请求从队列取行,不再有泄漏线程。

**回归测试**:`tests/test_engine_worker_race.py`(仅标准库,直接解析 app.py 提取类定义、以假 worker 模拟协议;`--real` 可对真实 `engine_worker.py` 冒烟,只需"ping"命令,不加载模型)。覆盖:慢 ready(旧实现泄漏读线程的首个请求必挂)后 12 个并发 ping 各拿各的 result、额外无 id 行(model_loaded)正确跳过、在途请求 kill 后快速报错且释放锁、后续请求自动重启 worker。离线与 `--real` 两种模式均通过。

**真实端到端验证(2026-09-06,RTX 4060 + wam_mit.pth)**:`tests/e2e_real_backend.py` 启动真后端(新代码),合成 4s/1080p60 测试视频,建测试作品后跑完整链路,任务时间戳如下(created→started→finished):

| 任务 | created | started | finished | 结果 |
|---|---|---|---|---|
| embed_video | 23:27:42 | 23:27:43 | 23:28:12 | done,PSNR 45.85,自检 acc=1.0 |
| extract#0(嵌入完成 +0s 提交) | 23:28:12 | 23:28:12 | 23:28:19 | hit,60/60 帧,策略 full |
| extract#1(+3s) | 23:28:15 | 23:28:19 | 23:28:21 | hit,60/60 帧 |
| extract#2(+6s) | 23:28:21 | 23:28:21 | 23:28:23 | hit,60/60 帧 |

## P2 —— 功能性缺陷,建议列入近期修复

## P3 —— 低危 / 健壮性 / 一致性建议

### 6. `common.read_frames` 的跳帧寻址硬编码 60fps
`src/common.py:173`:`-ss (start_frame - 0.5) / 60.0`。验收套件按 1080p60 设计属已知假设;但 `webui/engine_embed.py:67` 的成品自检抽帧也走这个函数——非 60fps 素材上"抽中段帧"会抽偏(仍能判 hit/miss,只是语义漂移)。建议把 fps 参数传进去,或改用 `-vf select` 精确寻帧。

### 7. `src/embed_video.py`(CLI)落后于引擎版的三处
- 帧数校验失败仅打印 ✗,不置非零退出码(`embed_video.py:138-140`)→ `run_all` 的 `assert rc==0` 拦不住坏成品(引擎版在 `engine_embed.py:157-158` 会 raise,是对的)。
- 成品同名直接覆盖(`-y` + 固定名),README 承诺的"_v2/_v3 尾缀"只有引擎版实现了。
- 异常路径 `enc.stdin.close()` 可能抛 BrokenPipeError 掩盖原始异常,且不杀残留 ffmpeg(`embed_video.py:116-120`);引擎版已用 try/except 包住(`engine_embed.py:131-141`)。CLI 与引擎两份 ~100 行嵌入逻辑长期双轨,建议收敛为一份(引擎版为基准)。

### 8. `webui/app.py` 若干小问题
- `_probe_cache` 定义了两次(`app.py:762` 与 `app.py:1002`,后者覆盖前者,前者成死代码);且该缓存按 `(name, mtime, size)` 累积、永不淘汰,文件被删除后条目残留。
- `/api/frame` 缓存键对 t 做 0.5s 取整(`app.py:720`),但 ffmpeg 用原始 t 解码:先请求 t=1.3 再请求 t=1.5 会拿到 1.3s 的帧。预览用途影响很小,建议键与解码参数用同一个取整值。
- 转码预览缓存文件名用 `abs(hash(str(p))) % 99999`(`app.py:811-812`):Python 进程级 hash 随机化,每次重启文件名都变 → `webui/data/preview_cache/` 里旧缓存变成永不清理的孤儿文件(且有小概率哈希冲突互串)。建议改用稳定的 md5(path) 并加启动期清理。
- `under_proj()` 与 `_check_preview_path()` 用 `startswith` 判前缀且不带路径分隔符(`app.py:72-77`、`740-748`):理论上 `F:\Project\watermark2\...` 能通过 `under_proj` 校验(`F:\Project\watermark` 是它的前缀)。仅本机单用户、风险低,但修复成本一行(resolve 后补 `os.sep`),建议顺手改。
- `JobStore._load()` 在 jobs.json 损坏时静默清空历史(`app.py:116-120`),建议至少在日志里留一句。
- `api_upload` 无大小上限(流式写盘本身没问题,属可接受的本机权衡)。

### 9. `src/verify.py` 小项
- `run_segment(..., wam=None)` 形参从未被传入非 None 值,每段各重载一次模型(两次共浪费一次 ~10s 加载);`--segment` 文档串与实际参数 `--start` 不一致。
- `prod_seg` 中转文件"存在即复用"(`verify.py:73-74`):上次运行被打断留下的半截 mp4 会被当作有效缓存,后续所有攻击项都在坏数据上测。建议写入 `.part` 完成后改名,或校验帧数。

### 10. `common.load_wam` 静默吞掉 JND 配置失败
`src/common.py:138-141`:`except Exception: attenuation = None`——若 params.json/配置不匹配,水印将退化为无 JND 掩码的均匀嵌入,**画质与鲁棒性双双改变且无任何提示**。至少应打印警告。

### 10b. `torch.load` 触发弃用警告(真实测试日志中发现)
`src/common.py:143`:`torch.load(REPO / "checkpoints" / ckpt_name, map_location="cpu")` 未传 `weights_only`,每次加载都打印 FutureWarning("In a future release, the default value for `weights_only` will be flipped to True")。权重是本项目自有的 `wam_mit.pth`,无投毒面,但建议显式 `weights_only=True`(该权重为纯 state_dict,可安全开启)并顺带消除日志噪音——`engine_worker` 常驻进程每次启动都会刷一遍。

### 11. `store.add_work` 对 v1 码本不迁移
`webui/store.py:62-65`:若码本还是 v1 且 `add_work` 是第一个被调用的操作(任何 `load()` 之前),会报"码本格式异常"而不是自动迁移。实际 UI 流程几乎总是先触发 `load()`,属边缘场景,知悉即可。

### 12. 前端 `static/app.js`
- **上传通道缺 probe**:`sourcePicker` 的上传分支只存 `{path, name, size_mb}`(`app.js:224`),而提取页完全依赖 `s.probe` 渲染时长/时间条(`app.js:563-571`)→ **上传的视频在"查水印"页没有时间选择条**(只能以 t=0 提交)。建议上传完成后补调一次 `/api/probe`。
- `PAGES.embed` 里的 `isVideoSrc()`(`app.js:398`)是死代码。
- 其余抽查无虞:`esc()` 转义覆盖一致,前端 `deriveId` 与后端 `derive_id` 算法一致,内联 `onclick` 注入的均为后端生成的安全 id。

## 值得肯定的设计(保持)

- `webui/store.py`:tmp+replace 原子写、RLock 可重入、v1→v2 迁移、ID/文本双重冲突校验,是干净的小存储层。
